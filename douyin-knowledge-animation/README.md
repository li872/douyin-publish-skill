# 这个技能为什么是三个文件？（新人必读）

```
douyin-knowledge-animation/
├── SKILL.md      ← 入口：主流程 + 硬性规范（每次触发必读）
├── tech-spec.md  ← 附录：技术骨架 + 代码模式（写代码时才读）
├── publish.md    ← 附录：发布策略 + 流量机制（问怎么发时才读）
└── README.md     ← 本文件，给人看的说明，AI 不加载
```

## 一句话原因

**AI 的"工作记忆"是有限的。技能入口（SKILL.md）每次触发都会被完整读入，
而附录文件只在用到时才读——所以要把"每次都需要的"和"偶尔才需要的"拆开放。**

这个做法在技能编写规范里叫 **渐进式披露（Progressive Disclosure）**：
先给必需的骨架，细节按需展开，就像菜谱封面只印核心步骤，详细火候写在内页。

## 三个文件各管什么

| 文件 | 内容 | AI 什么时候读它 | 对应工作阶段 |
|---|---|---|---|
| SKILL.md | 爆款格式公式、6 步工作流、金句写法、可读性硬规范、验证方法 | 技能触发时必读 | 策划内容 |
| tech-spec.md | 720×1280 HTML 骨架、CSS 定稿数值、JS 关键代码、常见坑 | 动手写动画代码时 | 制作动画 |
| publish.md | 抖音推流机制、剪映踩点流程、文案模板、发布时间 | 用户问发布相关问题时 | 发布运营 |

## 为什么不合成一个大文件？

**1. 省 AI 的注意力（最重要）**
上下文窗口是 AI 和任务共用的。技能正文越长，占用越多，留给实际任务
（写代码、拆分镜）的空间越少。写动画时不需要"晚 7~10 点发布"这种知识，
读进来纯属浪费。

**2. 三块内容的"保质期"不同**
- SKILL.md：踩坑打磨出的硬规范（安全区、纯白字体、最小 16px），基本不变
- tech-spec.md：代码实现，换设计风格时只改它
- publish.md：平台机制，抖音算法年年变，它最先过时——过时了单独更新，不牵连其他

**3. 对应真实工作流的三个阶段**
策划内容 → 制作动画 → 发布运营。哪个阶段出问题改哪个文件，边界清晰，
多人协作或日后维护都不容易改乱。

## 维护约定

- 改规范/流程 → 改 SKILL.md（保持 500 行以内，超了就往附录挪）
- 改代码模式/骨架 → 改 tech-spec.md
- 平台机制变了 → 只改 publish.md
- 附录只允许被 SKILL.md 直接链接（一层深度），不要附录再套附录，AI 可能读不全
- 本 README 是写给人看的；AI 触发技能时只认 SKILL.md 和它链接的文件
